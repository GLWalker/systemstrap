That clarification changes the diagnosis in an important way.

Your panel is not trying to behave like a generic Gutenberg Group with decorative styling. It is a **layout primitive**, equivalent to a Bootstrap card shell:

```txt
system-ui-panel
├── system-ui-header
├── direct content
└── system-ui-footer
```

The intended contract is:

* the panel wrapper owns border, radius, background, shadow, and clipping;
* recognized structural children such as header and footer own their own spacing;
* direct component children sit flush against the panel edges;
* ordinary textual content receives panel-body spacing automatically;
* nested Groups create deliberate spacing boundaries;
* deeper descendants retain their own authored spacing.

That is a coherent component model. You do not need a mandatory `system-ui-content` wrapper merely to satisfy CSS purity.

## Your nesting rule makes sense

This:

```txt
panel
└── group
```

should make the direct Group fill the panel’s usable width without adding another unnecessary outer gutter.

This:

```txt
panel
└── group
    └── group
```

should allow the inner Group to retain its own padding because it is now content inside the first Group, not a direct panel section.

That is a useful and understandable rule:

> The panel normalizes its direct children. Descendants beyond the first structural level remain under normal Gutenberg layout control.

That rule can be implemented without dozens of `:has()` selectors.

## The real distinction is not “wrapped versus unwrapped”

The important distinction is:

### Flush direct components

These should touch the panel edges:

* Group
* Cover
* Query
* Navigation
* styled List blocks
* Accordion
* Tabs
* system header
* system footer
* other intentionally sectional components

### Body-like direct content

These should receive panel padding automatically:

* Paragraph
* Heading
* Quote
* Code
* Preformatted
* Verse
* Table, depending on desired visual behavior
* individual Buttons
* other inline-content-oriented blocks

### Special direct media

Images need their own rule because WordPress’s Image block is:

```html
<figure class="wp-block-image">
	<img>
</figure>
```

The figure is the block wrapper. The image itself should not be receiving panel-style spacing independently.

So the issue is not that your overall model is wrong. The issue is that the current selectors are trying to infer these categories through too many descendant conditions.

## You can simplify the panel considerably

The panel can work from direct-child defaults and a relatively short exception list.

Conceptually:

```css
.system-panel {
	overflow: hidden;
}

/* Direct children are structural sections by default. */
.system-panel > * {
	inline-size: 100%;
	max-inline-size: none;
	margin-block: 0;
}

/* Text-like direct blocks receive body spacing. */
.system-panel > :is(
	p,
	h1,
	h2,
	h3,
	h4,
	h5,
	h6,
	blockquote,
	pre,
	.wp-block-code,
	.wp-block-verse
) {
	padding-inline: var(--system-panel-padding-inline);
	padding-block: var(--system-panel-padding-block);
}

/* Structural block sections remain edge-to-edge. */
.system-panel > :is(
	.wp-block-group,
	.wp-block-cover,
	.wp-block-query,
	.wp-block-navigation,
	.wp-block-details,
	.wp-block-list,
	.wp-block-image
) {
	padding: 0;
}
```

That is only illustrative, because the exact blocks depend on your theme’s inventory, but the architecture is much simpler:

1. Normalize direct children.
2. Add body padding to direct text-oriented blocks.
3. Give known System UI components their own internal contract.
4. Do not inspect deeply nested descendants unless absolutely necessary.

## Paragraphs are the legitimate reason for automatic panel-body spacing

You are right that requiring:

```txt
panel
└── group
    └── paragraph
```

for every paragraph would be pointless markup inflation.

A panel should reasonably support:

```txt
panel
└── paragraph
```

and make it look correct automatically.

The same applies to headings and other ordinary content blocks.

That is not “overriding Gutenberg recklessly.” It is the expected behavior of the selected panel style.

When a user selects `System Panel`, they are choosing a component contract. It is fair for that contract to say:

* direct paragraphs get body padding;
* direct headers and footers get their own spacing;
* direct sectional components are flush.

## Images should be treated as blocks, not as nested images

The Image issue should probably be solved by targeting the direct figure wrapper only:

```css
.system-panel > .wp-block-image {
	margin: 0;
	padding: 0;
	inline-size: 100%;
	max-inline-size: none;
}

.system-panel > .wp-block-image img {
	display: block;
	inline-size: 100%;
	max-inline-size: 100%;
}
```

Then preserve alignment and authored image dimensions where appropriate.

The dangerous version is something broad like:

```css
.system-panel img {
	padding: ...;
}
```

because that catches:

* images inside Query blocks;
* avatars;
* icons;
* nested Group images;
* Cover internals;
* plugin-generated media.

The direct-child figure should be the boundary.

You may also want a deliberate distinction between:

* direct full-bleed Image block;
* aligned or intentionally constrained Image block;
* image inside a padded Group.

For example, an image with an authored width smaller than the panel should not necessarily be forced to stretch. The figure can be flush while the image retains its width and alignment.

## The first nested Group rule is defensible

This behavior:

```txt
panel
└── group.default
```

where the direct Group is flush to the panel boundary is reasonable.

The Group itself then owns its internal padding through its own settings or theme defaults.

That means the panel does not need to determine how much content padding the Group should have. It only prevents Gutenberg’s outer constrained-layout behavior from inserting unintended width restrictions between the Group and the panel shell.

A clean rule may look more like:

```css
.system-panel > .wp-block-group {
	inline-size: 100%;
	max-inline-size: none;
	margin-inline: 0;
}
```

Notice what is absent:

```css
.system-panel > .wp-block-group {
	padding: 0 !important;
}
```

You probably do not want to erase user-authored padding from every direct Group.

The panel should remove unwanted outer geometry, not necessarily destroy the child Group’s internal spacing.

That distinction is important:

* `width`, `max-width`, and outer margins belong to the parent-child relationship;
* `padding` belongs to the child component itself.

## Your list-group model is also valid

Bootstrap-style list groups naturally want edge-to-edge behavior inside a card:

```txt
panel
├── header
├── list group
└── footer
```

The list group owns:

* item borders;
* item padding;
* active states;
* first/last item treatment;
* optional flush behavior.

The panel should not add generic body padding around that direct list.

Your flush variation then modifies list-group border and radius behavior, not the panel’s entire layout system.

That architecture is sound.

The main improvement would be to ensure the parent panel does not need to inspect the full internal list markup. It should only need to recognize the direct styled block:

```css
.system-panel > .is-style-system-list
```

The list stylesheet then handles its own descendants.

## `:has()` is probably unnecessary for most of this

Based on your explanation, the panel does not need to ask:

* whether a Group contains another Group;
* whether a Query contains an Image;
* whether a List has certain descendants;
* whether an editor wrapper contains a specific component.

Most behavior can be derived from the direct child itself.

Use `:has()` only for genuinely parent-dependent presentation states, such as:

```css
.system-panel:has(> .system-panel-header)
```

when the presence of a header changes the panel’s top-edge behavior.

Even there, sibling and direct-child rules may remove the need:

```css
.system-panel > .system-panel-header:first-child {
	border-start-start-radius: inherit;
	border-start-end-radius: inherit;
}
```

The panel should not need to reverse-engineer every composition.

## Your `theme.json` philosophy is correct

The flat baseline is a strong idea.

The theme provides:

* sensible global defaults;
* broadly usable Core blocks;
* user-configurable controls;
* custom CSS freedom;
* optional System UI transformations.

Then selecting a System UI style opts a block into a more opinionated framework-like contract.

That is exactly how block styles should feel:

```txt
Default block
→ neutral, flexible, theme-aware

System UI block style
→ opinionated, polished, framework-like
```

The style should not be judged by whether it preserves every default Core behavior. It should be judged by whether:

1. its overrides are intentional;
2. its contract is predictable;
3. its editor controls do not falsely imply unsupported behavior;
4. nested content escapes back into normal Gutenberg behavior at a clear boundary;
5. removing the style returns the block to a sane baseline.

Your panel appears to satisfy the intended conceptual model. The current problem is primarily implementation complexity, not architectural invalidity.

## I would restate the panel contract like this

> `System UI Panel` is an opinionated Group block style that creates a bordered component shell. Direct structural block children occupy the panel edge-to-edge. Direct text-oriented blocks receive automatic panel-body spacing. Header, footer, lists, navigation, media, query, accordion, tabs, and other System UI components own their internal spacing. Nested descendants retain their normal Gutenberg spacing and layout settings unless their own selected style defines otherwise.

That should go directly into the variation contract.

## The better refactoring direction

Do not add a compulsory content wrapper.

Instead:

* reduce behavior to direct-child rules;
* classify direct children by role;
* let child components own their internals;
* preserve padding on direct Groups unless intentionally overridden;
* target `.wp-block-image` rather than descendant `img`;
* reserve `:has()` for a few shallow composition states;
* remove editor-wrapper selectors from component logic where possible;
* create editor-only adapter rules separately.

So yes: with this explanation, I would soften the prior criticism substantially.

The panel is not accidentally overriding layout. It is intentionally defining a Bootstrap-card-like direct-child contract. The cleanup task is to express that contract more directly and with fewer inferred descendant states.

* the first image is clipped to the top corners;
* the last image is clipped to the bottom corners;
* a full-panel image gets all four corners;
* middle images stay square;
* Cover blocks, videos, and other media benefit from the same shell clipping;
* fewer child-specific radius rules are needed.

Explicit child radius rules may still be necessary when shadows, outlines, captions, or Safari rendering prevent shell clipping from producing the desired result.

This does not alter the color hierarchy. It creates a component-level handoff point.

## 4. Replace the enormous negative padding selector

The main maintenance problem is lines 73–80:

```css
.panel > *:not(...):not(...):not(...) {
	padding: var(...);
}
```

This says:

> Every unknown direct block is body content unless it appears in our growing exception list.

That is why the stylesheet keeps expanding.

Your clarified contract suggests a cleaner approach:

* every direct child spans the panel;
* component blocks retain their own spacing;
* only direct prose-like blocks receive automatic body padding.

I would replace the negative selector with positive body-content selectors:

```css
.wp-block-group.is-style-system-panel > :is(

	h1,
	h2,
	h3,
	h4,

		var(--strap-system-panel-padding-y)
```

Then add other body-like blocks only when their direct presentation actually needs panel padding.

Potential candidates:

```css
.wp-block-group.is-style-system-panel > :is(
	.wp-block-buttons,
	.wp-block-table,
	.wp-block-file,
	.wp-block-audio,

		var(--strap-system-panel-padding-x);

	margin-block:
		var(--strap-system-panel-padding-y);

```

Whether these should use margin or padding depends on how their own backgrounds and borders should behave.

The important change is that they are explicitly classified, rather than receiving padding because they failed an exclusion test.

## 5. Keep direct Groups full width without erasing their padding

The current normalization does this:

That general intent is correct, but I would make the complete direct-child contract explicit:

The Group spans the panel.

Its own padding is preserved.

Then:

```txt
Panel
└── Group
    └── Image
```

The Image is spaced by the Group because the panel does not reach through and modify it.

I would not apply:

* bottom corners when last;
* all corners when only child;
* no visible outer rounding when in the middle.

### Captions

## 7. Stop rounding every first and last child

The current stylesheet gives radius to all first and last direct children:

```css
.panel > *:first-child {
	border-top-left-radius: ...;
	border-top-right-radius: ...;
}

.panel > *:last-child {
	border-bottom-left-radius: ...;
	border-bottom-right-radius: ...;
```

This is unnecessary when the panel clips its content.

It may also create unwanted internal curves on:

* paragraphs with backgrounds;
* ordinary Groups;
* Query blocks;
* containers with their own border;
* list wrappers.

I would let the parent panel own the outer radius.

Use child radius only for components that need a matching background boundary when overflow is switched to visible, such as a panel containing Navigation.

## 8. Keep one smart overflow detection for Navigation

But it is currently broad. Any deeply nested Navigation causes the outer panel to stop clipping.

```css
.wp-block-group.is-style-system-panel:has(
```

Possibly also support a direct Group wrapper when that is part of a known navigation pattern:

```css
.wp-block-group.is-style-system-panel:has(

	> .wp-block-navigation:only-child

	overflow: visible;
```

Only add that second form if your saved patterns actually use it.

Once overflow becomes visible, targeted first/last radius rules may again be needed for direct media or header/footer blocks. That should be a small, explicit compatibility lane.

## 9. Remove nested one-child breakout hacks

Lines 82–95 use `:has()` and negative margins to undo padding added by the earlier generic rule:

```css
.panel > *:has(> list:only-child) > list {
	margin: calc(padding * -1);
}
```

and similarly for nested footers.

These rules exist because the stylesheet first pads an unknown wrapper and then discovers that the wrapper contains a flush component.

With the simpler direct-child model:

```txt
Panel
└── Group
    └── List
```

the Group should retain its own spacing. The List should not automatically escape that Group.

If the user wants the List flush to the panel, it should be a direct panel child:

```txt
Panel
└── List
```

That is predictable and matches your nesting philosophy.

I would remove the breakout rules entirely unless there is a WordPress editor wrapper—not an authored Group—causing the extra level. Editor wrappers should be handled in an editor adapter, not through generic frontend nesting logic.

## 10. Simplify list-group integration

The current list selectors support:

* direct lists;
* lists wrapped inside arbitrary direct children;
* editor wrappers;
* first and last item detection;
* appender detection.

This is where much of the `:has()` growth occurred.

The clean frontend rule should focus on a direct System List:

```css
.wp-block-group.is-style-system-panel

		.is-style-system-list-flush

	margin: 0;
	border-radius: 0;
```

Then flatten the list item side borders:

```css
.wp-block-group.is-style-system-panel

	> :is(li, a) {
	border-inline: 0;
	border-radius: 0;
	box-shadow: none;
```

Because the panel owns the outer border and clips its children, first and last list items often do not need their own outer radius.

If the panel overflow is visible due to Navigation, that should not affect a sibling list’s clipping unless the whole shell no longer clips. In that case, a targeted panel state variable or wrapper strategy would be more reliable than reproducing all radius rules.

### Double borders

Queries and other list-producing components can be added positively if they directly precede the footer.

## 12. Replace the broad nested-chrome rule with a variable chain

The final rule currently says:

```css
.panel :is(.system-list, .system-list-flush) > li,
.panel :is(.system-list, .system-list-flush) > a,
.panel .system-panel {
	background-image: none !important;
	backdrop-filter: none !important;
}
```

This is structurally broad and hard-coded.

Your nested color model deserves a variable-based solution.

At the panel root, define:

```css
.wp-block-group.is-style-system-panel {
	--strap-system-panel-surface:
		var(--wp--custom--system-ui-surface);

	--strap-system-panel-background-image:
		var(--wp--custom--system-ui-background-image, none);

	--strap-system-panel-backdrop-filter:
		var(--wp--custom--system-ui-backdrop-filter, none);
}
```

Then inside a System UI panel, redefine the System UI defaults inherited by nested System UI components:

```css
.wp-block-group.is-style-system-panel {
	--wp--custom--system-ui-surface:
		var(--wp--custom--system-ui-surface-nested, transparent);

	--wp--custom--system-ui-background-image:
		var(--wp--custom--system-ui-background-image-nested, none);
}
```

However, this must be ordered carefully.

If you override the global variables on the same element before the panel consumes them, the current panel could accidentally become transparent too.

The safest pattern is:

```css
.wp-block-group.is-style-system-panel {
	/* Capture current-level values first. */
	--strap-system-panel-surface:
		var(--wp--custom--system-ui-surface);

	--strap-system-panel-background-image:
		var(--wp--custom--system-ui-background-image, none);

	--strap-system-panel-backdrop-filter:
		var(--wp--custom--system-ui-backdrop-filter, none);

	background-color: var(--strap-system-panel-surface);
	background-image: var(--strap-system-panel-background-image);
	backdrop-filter: var(--strap-system-panel-backdrop-filter);
}

/* Descendants inherit nested System UI defaults. */
.wp-block-group.is-style-system-panel > * {
	--wp--custom--system-ui-surface:
		var(--wp--custom--system-ui-surface-nested, transparent);

	--wp--custom--system-ui-background-image:
		var(--wp--custom--system-ui-background-image-nested, none);

	--wp--custom--system-ui-backdrop-filter:
		none;
}
```

This is much closer to the chain you described:

```txt
Current component captures current System UI layer
↓
Its descendants inherit nested System UI layer
↓
Nested System UI components consume the nested values
```

That avoids stacked translucent surfaces becoming progressively darker.

## Critical concern: CSS custom-property self-reference

Be careful not to write:

```css
.panel {
	--wp--custom--system-ui-surface:
		var(--wp--custom--system-ui-surface-nested);
}
```

and then try to use the original value later on that same element.

Custom properties resolve from the computed cascade, not in top-to-bottom procedural order.

That is why component aliases are important: capture the current intended values through separate names, then change what descendants inherit.

## 13. Border nesting should follow the same model

The default border color is:

```css
color-mix(in srgb, currentColor 30%, transparent)
```

A nested component with the same translucent border can create doubled lines or darker junctions.

I would define:

```css
.wp-block-group.is-style-system-panel {
	--strap-system-panel-border-color:
		var(--wp--custom--system-ui-border-color);

	border-color: var(--strap-system-panel-border-color);
}
```

Then descendants can inherit a nested border token:

```css
.wp-block-group.is-style-system-panel > * {
	--wp--custom--system-ui-border-color:
		var(
			--wp--custom--system-ui-border-color-nested,
			var(--wp--custom--system-ui-border-color)
		);
}
```

Your current `theme.json` does not appear to define:

```css
--wp--custom--system-ui-border-color-nested
```

I would add it.

A reasonable default may be:

```json
"system-ui-border-color-nested": "color-mix(in srgb, currentColor 18%, transparent)"
```

or:

```json
"system-ui-border-color-nested": "transparent"
```

The correct choice depends on whether nested components should retain subtle internal boundaries.

Given your list-group and panel model, I suspect a lighter nested border—not universally transparent—would be more useful.

## 14. User-selected block colors must remain highest authority

The nested variable chain must not erase WordPress classes such as:

```css
.has-background
.has-text-color
.has-border-color
```

or inline style values generated by block supports.

I would not use `!important` on panel color declarations.

For example:

```css
.panel:not(.has-background):not([style*="background"]) {
	background-color: var(--strap-system-panel-surface);
}
```

The background image overlay can remain active independently:

```css
.panel {
	background-image: var(--strap-system-panel-background-image);
}
```

Thus:

```txt
User background-color
+ System UI translucent background-image
```

continues to work.

For borders, when the user chooses a block border color, WordPress may emit a class or inline declaration. The panel rule should not automatically replace it.

The current rule:

```css
.panel.has-background {
	border-color: var(--wp--custom--system-ui-border-color);
}
```

is suspicious.

A background selection does not necessarily imply the user did or did not choose a border color.

I would remove that rule or narrow it so a user-selected border remains authoritative.

Recommended fallback:

```css
.wp-block-group.is-style-system-panel:not(.has-border-color) {
	border-color: var(--strap-system-panel-border-color);
}
```

If WordPress emits inline border color without `.has-border-color`, account for the actual saved markup, but do not connect border authority to `.has-background`.

## 15. Preserve dynamic foreground color

You noted that foreground colors are created through WCAG contrast comparison against the background.

The panel stylesheet should not assign a hard-coded `color`.

It currently does not, which is good.

Keep text color inherited unless:

* the block editor supplies `.has-text-color`;
* a dynamic style system assigns a contrast-safe color;
* a variation explicitly opts out.

The border’s use of `currentColor` is particularly clever because it follows the resolved foreground contrast color.

That means:

```css
system-ui-border-color:
	color-mix(in srgb, currentColor 30%, transparent)
```

automatically harmonizes with the contrast-selected text color.

I would preserve that.

# What I would add

## A documented nested System UI inheritance contract

Add a compact contract in CSS comments:

```css
/*
 * System UI nesting contract:
 *
 * 1. A component captures the current System UI surface, border,
 *    background-image and filter values into local aliases.
 *
 * 2. Its direct descendants inherit the nested System UI values.
 *
 * 3. Nested System UI components consume those inherited values,
 *    preventing translucent surfaces and filters from stacking.
 *
 * 4. WordPress block-editor colors remain authoritative through
 *    block support classes and inline custom properties.
 */
```

That will prevent future audits from replacing the deliberate variable chain with hard-coded `background: none`.

## A nested border token in `theme.json`

Add:

```json
"system-ui-border-color-nested": "color-mix(in srgb, currentColor 18%, transparent)"
```

or transparent, depending on the intended default look.

This gives variations a proper override point.

Rather than a generic “everything else” selector, define the ordinary direct blocks that become body content.

```css
		var(--strap-system-panel-padding-y)
```

# What I would remove

I would remove or heavily reduce these areas:

* The blanket direct-child `border-radius: 0 !important`.
* The long `:not()` padding selector.
* The duplicate modal version of that same selector.
* Nested one-child breakout rules using negative margins.
* Nested footer breakout rules.

* parent clipping;
* variable inheritance;
* a small number of editor adapter rules.

```css
		.is-style-system-details
	)
	+ .is-style-system-panel-footer {
	border-block-start: 0;
}

/* Only direct navigation changes panel overflow. */
.wp-block-group.is-style-system-panel:has(
	> .wp-block-navigation
) {
	overflow: visible;
}
```

## Final assessment

The current file is doing the correct jobs, but often in the wrong order:

1. It applies generic padding.
2. It detects components that should not have that padding.
3. It uses negative margins to undo it.
4. It detects nested structures to restore edge behavior.
5. It strips backgrounds and filters after translucent layers stack.

The better order is:

1. Capture the current color and visual layer.
2. Pass nested visual variables to descendants.
3. Make all direct children full width.
4. Add padding only to direct body content.
5. Let direct System UI components remain flush.
6. Leave deeper nested blocks alone.
7. Handle only genuine edge states with shallow selectors.

That preserves your three-level color system, respects nested transparency, and should remove a large portion of the file without reducing the polished result.

The guide confirms that nested System UI surfaces deliberately disable repeated visual effects:

```txt
List file

Details file

Query file
```

## One thing I would add to the guide

The current guide says nested surfaces must not double-stack, but it does not state the structural boundary clearly enough.

I would add:

```css
/*
 * Panel direct-child contract
 *
 * - Every direct child spans the panel's available width.
 * - Direct prose blocks receive panel-body spacing.
 * - Direct System UI components join the panel shell and flatten
 *   their adjoining outer chrome.
 * - Direct Group blocks retain their authored internal padding.
 * - Components nested inside an authored Group are not treated as
 *   direct panel sections.
 * - Nested System UI visual effects use the existing nested tokens
 *   to avoid stacked translucent surfaces, borders and filters.
 */
```

That single contract would prevent another audit from reintroducing wrapper breakout selectors.

## My revised recommendation

Use `docs/guides/system-ui.css` as the review map, but update the runtime files by ownership.

For the panel file:

* keep its direct variable usage;
* keep its background authority behavior;
* make every direct child full width;
* positively pad direct body content;
* keep direct Image and Cover blocks flush;
* preserve direct Group padding;
* limit List, Accordion, Details, Query, Header, and Footer joining to direct children;
* retain shallow first/last radius detection;
* remove arbitrary-wrapper breakout logic;
* remove deep `:has()` component inference.

For the other System UI files:

* keep their own nested surface and border behavior;
* consume the established nested variables;
* avoid double shading when inside another System UI component;
* preserve editor-selected background, border, and text colors as the final block-level authority.

That will simplify the panel substantially without flattening the color system or weakening the framework-like polish.

```css
.wp-block-group.is-style-system-panel
```

```txt
    └── Figure/Image       → Group controls its spacing
```

```css
.panel > div {
```

```css
.wp-block-group.is-style-system-panel
```

1. The Panel itself has no padding.
2. Every direct child escapes constrained content width.
3. Direct figures are flush.
4. Direct paragraphs and headings receive panel-body spacing.
5. Direct structural containers preserve their own internal padding.
6. Anything nested inside those containers is left alone.
7. System Header, Footer, List, Query, Accordion, and similar styles add only their specific joining and radius behavior.

That should replace most of the block-by-block exclusion list without sacrificing nesting behavior.
