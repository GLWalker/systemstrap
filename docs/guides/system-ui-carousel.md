# SystemStrap Carousel Cleanup — Codex Implementation Brief

## Objective

Refactor the SystemStrap carousel so that saved WordPress content contains only:

1. The carousel root block.
2. The authored slide blocks.
3. Stable configuration or intent markers.

Splide-specific wrappers, navigation controls, pagination elements, accessibility relationships, and runtime state must be generated by JavaScript.

Separately, replace the current narrow carousel asset gate with detection that covers carousels rendered outside singular post content.

Do not remove or replace the existing block variations and patterns. They remain the authoring and curated-default layer.

## Governing source

Before changing code, read:

```text
docs/START.md
docs/contracts/carousel-runtime.md
```

Update `docs/contracts/carousel-runtime.md` in the same change set whenever the saved markup contract, JavaScript ownership boundary, navigation behavior, or asset-loading behavior changes.

`docs/START.md` explicitly identifies that contract as authoritative for carousel variations, runtime JavaScript, runtime CSS, navigation positioning, sizing, and Splide ownership.

## Required architecture

### Saved content owns

The block variation or pattern must save:

- one stable carousel root
- the original Image, Cover, Group, list, or other supported slide blocks
- stable carousel type markers
- stable navigation-position markers
- intentional carousel options that must survive editing

Example conceptual saved structure:

```html
<div class="wp-block-group system-carousel has-nav-bottom">
	<figure class="wp-block-image">...</figure>
	<figure class="wp-block-image">...</figure>
	<figure class="wp-block-image">...</figure>
</div>
```

Do not serialize:

- navigation wrapper Groups
- Core Button navigation controls
- placeholder `href="#"` links
- Splide track wrappers
- Splide list wrappers
- Splide pagination markup
- runtime accessibility attributes
- mounted-state classes

### JavaScript owns

JavaScript must generate:

```text
splide__track
splide__list
previous button
next button
pagination when configured
ARIA labels and relationships
mounted and sizing state classes
```

The original authored slide elements must be moved into the generated Splide structure. Do not clone or replace them.

That preserves image markup, captions, links, block classes, IDs, responsive image attributes, and third-party behavior attached to the original elements.

### Splide owns

Splide continues to own:

- dragging
- translation
- snapping
- active-slide state
- movement boundaries
- pagination behavior
- carousel lifecycle after mounting

Do not duplicate Splide movement calculations in CSS.

### CSS owns

CSS continues to own:

- visual control styling
- control placement
- top, bottom, left, right, and center-out layouts
- gutters and presentation
- pre-mount fallback presentation
- explicit runtime-state presentation

Reuse the existing navigation-position classes and calculated layout areas where possible. Do not move those calculations into saved wrapper blocks merely to make positioning easier.

## Phase 1 — Simplify the block variations

Modify:

```text
assets/js/variations/strap-carousel.js
```

For each carousel variation:

1. Preserve the root carousel Group.
2. Preserve the actual authored slide blocks.
3. Preserve variation metadata as a human-readable editor label.
4. Preserve stable machine-readable carousel classes or attributes.
5. Remove saved navigation wrapper Groups.
6. Remove saved Core Button previous/next controls.
7. Remove empty layout blocks that exist only to position navigation.

The variation must still provide a complete usable starting composition when inserted.

Do not use `metadata.name` as the sole machine identifier. Metadata is editable and intended for humans.

Use a stable exact class such as:

```text
system-carousel
```

Add more specific intent classes only where required:

```text
is-system-thumbnail-carousel
is-system-standard-carousel
has-nav-top
has-nav-bottom
has-nav-left
has-nav-right
has-nav-center-out
```

Reuse existing class names when they already represent these contracts. Avoid inventing parallel names.

## Phase 2 — Generate runtime structure

Modify:

```text
assets/js/carousel-nav.js
```

For each uninitialized carousel root:

1. Collect the direct authored slide elements before modifying the DOM.
2. Create a `splide__track` element.
3. Create a `splide__list` element.
4. Add `splide__slide` to each authored slide element.
5. Move each authored slide into the generated list.
6. Append the list to the track.
7. Insert the track into the carousel root.
8. Generate actual `<button type="button">` controls.
9. Add accessible labels to both buttons.
10. Insert the controls into a generated controls container.
11. Apply the current navigation-position contract.
12. Initialize Splide only after the required DOM exists.
13. Store the runtime instance and cleanup data without duplicating global registrations.

Conceptual structure after JavaScript initializes:

```html
<div class="wp-block-group system-carousel splide has-nav-bottom">
	<div class="splide__track">
		<div class="splide__list">
			<figure class="wp-block-image splide__slide">...</figure>
			<figure class="wp-block-image splide__slide">...</figure>
		</div>
	</div>

	<div class="system-carousel-controls">
		<button type="button" class="system-carousel-prev">
			<span class="screen-reader-text">Previous slide</span>
		</button>

		<button type="button" class="system-carousel-next">
			<span class="screen-reader-text">Next slide</span>
		</button>
	</div>
</div>
```

Use translation-ready strings if labels are passed from PHP. Do not hard-code inaccessible icon-only controls without an accessible name.

Prevent duplicate initialization with a stable runtime flag or registry check.

## Phase 3 — Make teardown reversible

Add an explicit destruction path.

Teardown must:

1. Disconnect any `ResizeObserver`.
2. Remove fallback resize listeners.
3. Destroy the Splide instance.
4. Remove generated pagination.
5. Remove generated controls.
6. Remove generated track and list wrappers.
7. Move the original authored slide elements back into the carousel root.
8. Remove `splide__slide` and runtime-only attributes from those elements.
9. Remove runtime state classes.
10. Remove the instance from the runtime registry.

The result after teardown must closely match the original saved DOM.

Expose initialization and destruction through the existing SystemStrap namespace rather than adding unrelated globals.

Preferred shape:

```js
window.Strap = window.Strap || {}

Strap.initCarousels = function (scope) {}
Strap.destroyCarousels = function (scope) {}
```

Preserve an existing public initializer as a compatibility alias if project source shows that other code already calls it.

Do not break dynamic reinitialization merely to clean up the namespace.

## Phase 4 — Update editor controls

Modify:

```text
assets/js/variations/strap-controls.js
```

The navigation-position Inspector control must identify carousel roots through the stable carousel marker, not through a partial match against `metadata.name`.

Bad identity:

```js
metadataName.includes("Carousel")
```

Preferred identity:

```js
className.split(/\s+/).includes("system-carousel")
```

Use the project’s actual attribute shape and coding conventions.

The control should continue to save only intent, such as:

```text
has-nav-center-out
```

It must not insert navigation blocks into serialized content.

## Phase 5 — Adapt the carousel CSS

Modify:

```text
assets/css/style-variations/core-group-system-carousel.css
```

Update selectors to target the generated controls rather than saved Core Button blocks.

Preserve the existing calculated placement behavior for:

- top navigation
- bottom navigation
- left navigation
- right navigation
- center-out navigation

Rules:

1. Runtime-generated controls must inherit System UI presentation.
2. Controls must remain usable before and after Splide state changes.
3. CSS must not calculate or override Splide translation.
4. Pre-mount fallback rules must be scoped separately from mounted rules.
5. Do not depend on discarded wrapper Groups.
6. Keep selectors narrow enough that ordinary buttons outside a carousel are unaffected.
7. Retain visible focus styles.
8. Respect reduced-motion behavior already supplied by Splide or project CSS.

The generated controls container should be positioned from the root carousel’s intent class.

Do not create empty DOM regions merely to satisfy CSS grid placement. Use pseudo-grid areas, absolute positioning, flex placement, or the existing custom-property calculations as appropriate.

## Phase 6 — Open the enqueue gate

Modify:

```text
inc/enqueue-assets.php
```

The current gate must no longer rely only on searching the queried singular object’s raw `post_content`.

Carousel assets must load when a carousel is actually rendered from:

- post or page content
- templates
- template parts
- synced patterns
- server-rendered blocks
- archive templates
- other block-rendered theme regions

### Preferred implementation

Use a render-aware enqueue trigger based on the stable carousel marker.

A practical WordPress approach is:

1. Register carousel assets without immediately enqueueing them.
2. Inspect rendered blocks through a narrowly scoped block-render filter.
3. Detect the exact carousel root marker in block attributes or rendered block content.
4. Enqueue Splide CSS, Splide JavaScript, carousel runtime JavaScript, and carousel CSS once.
5. Return the original block content unchanged.

Use the narrowest suitable hook available in the supported WordPress versions.

Prefer targeting `core/group` or the actual owning block type rather than running expensive detection logic against every block without discrimination.

### Timing constraint

Verify that assets enqueued during rendering still print in the correct document location.

CSS is the primary concern because block rendering can occur after `wp_head`.

Acceptable approaches include:

- enqueueing registered styles early when block parsing establishes carousel presence
- inspecting the resolved block tree before `wp_head`
- using render detection as a fallback for scripts and late-discovered content
- combining early block-tree detection with a render-aware safety net

Do not assume a `render_block` enqueue automatically solves stylesheet timing.

### Detection requirements

Detection must use a stable machine marker.

Do not search for:

- human metadata names
- button labels
- incidental Splide-generated markup
- generic words such as `carousel`

Prevent duplicate work with `wp_style_is()` and `wp_script_is()` or an equivalent narrow guard.

### Performance requirement

Do not globally enqueue Splide on every frontend request unless project testing proves that reliable conditional loading is impossible.

The goal is broader and more accurate conditional loading, not abandoning conditional loading.

## Phase 7 — Dynamic content behavior

The public initializer must accept a scope:

```js
Strap.initCarousels(document)
Strap.initCarousels(fragment)
```

It must initialize only matching descendants inside that scope.

The initializer must be idempotent:

- initialized carousels are skipped
- newly inserted carousels are mounted
- repeated calls do not duplicate controls or wrappers

Asset loading and DOM initialization are separate concerns.

If a carousel is injected into a page where the assets were never enqueued, JavaScript cannot initialize code that does not exist. Do not pretend the initializer solves server-side asset discovery.

Document that limitation unless the project already has a supported dynamic asset-loader contract.

## Phase 8 — Migration and backward compatibility

Existing content may already contain:

- carousel wrapper Groups
- navigation Groups
- Core Button previous/next controls
- current carousel metadata
- current runtime classes saved accidentally or intentionally

Do not silently leave legacy content doubled up with newly generated controls.

Implement one of these strategies:

### Preferred

Teach the runtime to recognize the legacy saved structure and reuse only its slide container while suppressing or removing the legacy navigation furniture at runtime.

Then provide a block deprecation or editor migration so that opening and saving the content converts it to the lean structure.

### Minimum acceptable

Detect legacy navigation wrappers at runtime and do not generate a second set of controls.

Document that old serialized wrappers remain until the content is resaved or manually migrated.

Do not perform irreversible database-wide content replacement from theme activation code.

A theme is not a migration plugin, and activation is no place for surprise surgery.

## Phase 9 — Contract documentation

Update:

```text
docs/contracts/carousel-runtime.md
```

The contract must explicitly state:

- variations and patterns own authored content and curated defaults
- saved content contains slides and durable intent only
- JavaScript owns Splide wrappers and navigation controls
- original slide elements are moved, not cloned
- teardown restores the original authored structure
- CSS owns presentation but not Splide movement
- PHP owns conditional asset discovery and server-provided settings
- metadata labels are not machine identity
- legacy serialized carousel structures and their compatibility behavior
- supported carousel variation names currently present in source

Resolve any mismatch between documented and registered carousel variations in the same change set.

## Acceptance criteria

### Saved markup

After inserting and saving every carousel variation:

- no previous/next Core Button blocks are saved
- no navigation-only Group blocks are saved
- no `splide__track` is saved
- no `splide__list` is saved
- no generated pagination is saved
- the original slide blocks remain directly represented in post content
- stable carousel intent survives save and reload

### Frontend

With JavaScript enabled:

- every carousel mounts once
- controls are generated once
- controls are native buttons
- all navigation positions render correctly
- thumbnail and medium sizing rules remain correct
- dragging, looping, pagination, and snapping behave as before
- captions, links, responsive images, and nested block content remain intact

With JavaScript disabled:

- authored slide content remains visible
- there are no dead `href="#"` navigation links
- content remains readable in document order

### Theme switching

After switching away from SystemStrap:

- slide images and authored slide content remain in the post
- there are no saved Splide wrappers
- there are no saved carousel navigation buttons
- harmless SystemStrap intent classes may remain
- content degrades into ordinary WordPress blocks

### Asset loading

Carousel assets load when the carousel comes from:

- direct page content
- a block template
- a template part
- a synced pattern
- an archive or non-singular render path

Carousel assets do not load on a page with no rendered carousel.

### Editor

- carousel controls remain available in the Inspector
- renaming block metadata does not remove carousel settings
- editor preview does not serialize generated controls
- editor and frontend retain matching sizing behavior

### Regression checks

Test at minimum:

1. Thumbnail image carousel.
2. Medium image carousel.
3. Mixed-content carousel.
4. Cover-based carousel, if still supported.
5. Every navigation position.
6. Underflow with too few slides.
7. Overflow with many slides.
8. Narrow mobile viewport.
9. Wide desktop viewport.
10. Multiple carousels on one page.
11. Carousel inside a template part.
12. Carousel from a synced pattern.
13. Repeated initialization call.
14. Runtime destruction and reinitialization.
15. Existing legacy carousel markup.
16. JavaScript disabled.
17. Theme switched to a default WordPress theme.

## Non-goals

Do not:

- replace Splide
- create a new custom carousel block
- move carousel rendering wholesale into PHP
- replace variations with template parts
- create one template part per slide
- globally enqueue all optional assets without first implementing reliable detection
- save generated runtime markup
- redesign the block stress-test pages
- change the settled contrast architecture
- add a framework, build system, or abstraction layer for this work

## Expected deliverables

1. Lean carousel variation markup.
2. JavaScript-generated Splide wrappers.
3. JavaScript-generated native navigation buttons.
4. Reversible runtime teardown.
5. Stable editor-side carousel identification.
6. Render-aware conditional asset loading.
7. Legacy-content compatibility.
8. Updated carousel runtime contract.
9. A concise change summary listing verified behavior and anything left unverified.
